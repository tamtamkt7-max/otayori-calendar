# おたよりカレンダー (Otayori Calendar) 🚀

園や学校から容赦なく配布されるプリント類や、LINE/メールで送られてくるスクリーンショットをスマートフォンのカメラで撮影するだけで、AI（Gemini 3.5/1.5 Flash）が自動で日時・持ち物・イベント名を高度に構造化データに変換し、アプリ内のカレンダーへ即時自動登録する子育て世代向けWeb/PWAアプリケーション。

将来的なネイティブスマホアプリ（iOS/Android）環境へのスムーズな移行・連携を絶対の前提とした、APIファースト設計で構築されています。

---

## 💰 収益化・原価防御ロジック（赤字絶対回避システム）

- **フリーミアムモデルを採用:**
  - **無料ユーザー:** 画面下部にWeb広告を表示。AI自動スキャンはサーバーサイド（Firestore）で厳密に制御され、**月間10回**に制限。これを超えた瞬間に403エラーでAPIコールを物理遮断し、APIコストの予期せぬ高騰を防ぎます（API破産防御のセキュリティ壁）。
  - **月額プレミアムユーザー（想定: 480円/月）:** 広告の完全非表示、AI自動スキャン制限の解除、パートナーとのカレンダーリアルタイム家族同期共有。
- **AI原価の最小化:** 画像認識およびテキスト構造化のエンジンとして、極めて高速かつ安価な `Gemini 3.5 Flash` を採用。サブスクリプション売上および広告収入が、API消費コストを完全にアウトパフォームする設計を維持しています。

## 🛠 本番用堅牢化 & 拡張機能 (追加機能)

本番環境の長期的な安定運用とセキュリティ、およびユーザー体験の向上のため、以下の機能を実装しています。

### 1. エラー監視・リアルタイム検知 (Sentry)
- **構成**: `@sentry/nextjs` によるフルスタックエラー追跡。
- **アーキテクチャ**:
  - APIルート (`/api/scan`, `/api/events`, `/api/webhook/stripe`) 内での例外をキャッチし、自動的にSentryサーバーに例外イベントを送信。
  - 本番環境でのサーバークラッシュ、Stripe署名検証失敗、Gemini APIのクォータ切れなどをリアルタイムで自動検知・通知します。

### 2. 自動メール通知 (Resend)
- **構成**: `resend` SDKを使用したトランザクショナルメール送信。
- **アーキテクチャ**:
  - Stripeの Webhook イベントを受け取り、プラン変更完了時に自動でメールを送信します。
  - **決済・アップグレード完了時**: プレミアムプランの特典紹介を含むウェルカムメールの送信。
  - **サブスクリプション解約完了時**: 解約処理が正常に行われたことを通知するメールの送信。
  - 送信先アドレスは、Stripe Checkoutに入力された最新のクライアントアドレス、またはStripe APIから直接取得した顧客データを元にします。

### 3. APIセキュリティ強化 (Firestore レートリミット)
- **構成**: Firestoreの書き込み履歴を活用したスライディングウィンドウ型レートリミッター。
- **アーキテクチャ**:
  - 不正スクリプトやDDoS攻撃、二重クリック防止のため、各重要APIルートでアクセス制限を実施。
  - **Checkout API**: 1分間に最大3回まで。
  - **AI Scan API**: 1分間に最大5回、1日に最大30回まで。
  - **Events API (保存・削除)**: 1分間に最大15回、1日に最大100回まで。
  - 制限を超過した場合は自動的に `HTTP 429 Too Many Requests` エラーを返却し、バックエンドのシステム負荷を防御します。

### 4. カレンダーUIの改善 (レスポンシブ刷新 & 週・月表示切り替え)
- **構成**: Tailwind CSS + Lucide React によるフルレスポンシブ設計。
- **機能**:
  - PC、スマホ、タブレットに完全対応したレイアウト。
  - 月カレンダーと週カレンダー（現在の選択日の週を7日分表示）の表示切り替えトグルの追加。
  - 予定の有無と予定登録者のカラー（パパ・ママ・子供など）に合わせた美しく整列するカラーバッジ。
  - スキャン実行時の高級感あふれるローディング・スケルトンアニメーション。

### 5. Google カレンダー双方向同期 (OAuth 2.0)
- **構成**: `googleapis` (Google Calendar API v3) + OAuth 2.0 認証フロー。
- **アーキテクチャ**:
  - アプリから「Google連携」ボタンを押し、Googleカレンダーの編集権限を承認。
  - 認可コードから取得したリフレッシュトークン等の認証情報を、セキュアなAES-256-CBC方式で暗号化してFirestore (`users/${userId}/security/googleOAuth`) に格納。
  - ユーザーがアプリ上でおたよりをスキャンして予定が保存、または手動で予定を作成・変更・削除した際、自動的にバックエンドでトークンの有効期限をチェック（必要に応じてリフレッシュトークンで自動更新）し、ユーザーのGoogleカレンダーに予定をシームレスかつリアルタイムに同期します。
  - 予定には `googleEventId` が紐づけられ、編集・削除時も同一イベントが追跡更新されます。

## 🔑 Google OAuth 2.0 設定手順 (管理者向け)

カレンダー連携機能を使用するためには、Google Cloud ConsoleでのOAuthクライアントIDの設定が必要です。

1. **Google Cloud Console** にログインし、新しいプロジェクトを作成または既存のプロジェクトを選択します。
2. **「APIとサービス」 > 「ライブラリ」** から、**Google Calendar API** を検索し、「有効にする」をクリックします。
3. **「OAuth同意画面」** を設定します：
   - **User Type**: **「外部 (External)」** を選択します（「内部（Internal）」に設定したままだと、一般のGoogleアカウントでログインしようとした際「組織内でのみ利用可能です」とエラーになります）。
   - スコープに `.../auth/calendar.events` (カレンダー the events) を追加します。
   - 公開ステータスが「テスト中」の間は、下部にある **「テストユーザー (Test users)」** にログインテストを行いたいGoogleアカウントのアドレスを明示的に追加・登録しておく必要があります。
4. **「認証情報」 > 「認証情報を作成」 > 「OAuthクライアントID」** をクリックします：
   - アプリケーションの種類: Webアプリケーション
   - **承認されたリダイレクトURI** に、以下の本番コールバックURLを追加します：
     `https://<your-vercel-domain>.vercel.app/api/auth/google-calendar/callback`
     （ローカル開発時は `http://localhost:3000/api/auth/google-calendar/callback` も併記可能）
5. 生成された **クライアントID** と **クライアントシークレット** を、環境変数 `GOOGLE_CLIENT_ID` および `GOOGLE_CLIENT_SECRET` に設定します。
6. 暗号化用のキーとして、`ENCRYPTION_KEY` に十分な長さ（32文字以上推奨）のランダムな文字列を設定してください。

## 💰 マネタイズ設定手順 (Stripe & AdSense 管理者向け)

本アプリの収益化機能（サブスクリプションおよび広告配信）を正常に動作させるため、以下の設定を行います。

### 1. Stripe サブスクリプション商品 (Price ID) の設定
本番環境でアドホックなインライン価格生成を避け、Stripe ダッシュボードで固定登録された商品（月額480円プランなど）に紐付けるため、Price ID を定義します。

1. **Stripe ダッシュボード**（本番環境または開発用テスト環境）にログインします。
2. **「商品」 > 「商品を追加」** から以下を設定して保存します：
   - 商品名: `おたよりカレンダー プレミアムプラン`
   - 料金形態: `継続（サブスクリプション）`
   - 請求周期: `月次`
   - 価格: `480 JPY`
3. 作成された商品の詳細画面で、**「API ID」（例: `price_1Qxxxx...`）** をコピーします。
4. この ID を環境変数 `NEXT_PUBLIC_STRIPE_PRICE_ID` に設定します。設定されている場合、アプリは最優先でこの Price ID を使用してセッションを生成します。（未設定の場合はインラインで価格が自動生成されるフォールバックが働きます）

### 2. Google AdSense の設定
ユーザー（非プレミアム）に広告を表示し、最適に配信するための設定です。

1. **Google AdSense** にログインし、広告を作成（ディスプレイ広告など）して**広告ユニットのスロットID**を取得します。
2. アカウントの**パブリッシャーID**（例: `ca-pub-5461809032953003`）を環境変数 `NEXT_PUBLIC_ADSENSE_CLIENT_ID` に設定します。
3. アプリ上の広告は `AdBanner` コンポーネントを通じて自動レンダリングされます：
   - **配置箇所**: カレンダー下部、サイドバー下部、およびAIスキャン完了結果画面。
   - **非表示ロジック**: ユーザーがプレミアムプランを購読している場合（Firestore上で `plan` が `premium` の場合）、`AdBanner` コンポーネントは完全に `null` を返してレンダリングを回避します。
   - **スクリプトの最適化**: 広告読み込み用のGoogle AdSenseスクリプトは、Next.jsの `next/script` を通じて `strategy="afterInteractive"` で非同期的に非ブロッキングロードされます。

### 3. Firebase Web Push通知 (FCM) の VAPID 設定
予定の3日前・前日の通知（リマインド）機能を有効にするための設定です。

1. **Firebase コンソール** にログインし、対象プロジェクトを開きます。
2. 左上の歯車マーク ⚙ ➔ **「プロジェクトの設定」** を開きます。
3. **「Cloud Messaging」** タブをクリックします。
4. 下部にある **「ウェブ設定 (Web configuration)」** セクションの **「ウェブプッシュ証明書 (Web Push certificates)」** に移動します。
5. 表示されている **「鍵ペア (Key pair)」** の文字列（非常に長い英数字）をコピーします（※まだ作成されていない場合は「鍵ペアの生成」ボタンをクリックして新規発行してください）。
6. コピーしたキーを、環境変数 **`NEXT_PUBLIC_FIREBASE_VAPID_KEY`** に設定します（Vercelの環境変数および `.env.local` への登録が必要です）。

### 4. Google Analytics 4 (GA4) の設定
ユーザーの重要アクション（AIスキャン開始/成功、決済アップグレードクリック、通知ON、カレンダー連携）を追跡・効果測定するための設定です。

1. **Google Analytics** にログインし、新しいGA4プロパティを作成します。
2. データストリームの追加で「ウェブ」を選択し、本番環境のドメイン（例: `otayori-calendar-owfg.vercel.app`）を登録します。
3. 生成された **「測定ID」（例: `G-XXXXXXXXXX`）** をコピーします。
4. コピーした測定IDを、環境変数 **`NEXT_PUBLIC_GA_ID`** に設定します（Vercelの環境変数および `.env.local` への登録が必要です）。

### 5. PWA (iOS通知最適化) および Google 審査対策の法的ページ設定
iOS (Safari) における通知の許可基準と、Google OAuth 審査を通過するための法的要件に関する設定です。

1. **iOS 向け PWA 通知ガイド**:

   - iOS 且つ非スタンドアロンモードで通知設定を行おうとした場合、自動的に「ホーム画面に追加」の手順を解説するガイダンスモーダルがポップアップ表示されます。
2. **法的ページの設定と Google OAuth 審査**:

### 6. iOS / Safari 向けの互換性およびデバッグ対策
iOS (Safari) 環境で発生しやすいエラーや挙動不整合に対する対策です。

1. **日付パースの堅牢化 (Safari対策)**:
   - Safari の古い・厳格なパーサー仕様に対応するため、日付文字列（"YYYY-MM-DD"形式）のハイフンを自動でスラッシュ（"YYYY/MM/DD"形式）に置換してからパースする `safeParseDate` ヘルパーを適用しています。
2. **Stripe決済画面リダイレクト時のセキュリティブロック回避**:
   - 非同期処理後に `window.location.href` を書き換える際、Safariやアプリ内ブラウザ（WebView）がポップアップブロックやセキュリティ違反と誤検知してクラッシュするのを防ぐため、`try-catch` と `window.location.assign`、さらには `window.open` による多重フォールバック構造を実装しています。
3. **データ読み込み失敗時のエラー解説強化**:
   - Firebase Authentication のログイン後に Firestore からの読み込みで `permission-denied` (セキュリティルール拒否) が発生した際、単に「データの読み込みに失敗しました」と出すのではなく、Firebaseコンソール上でのルールの公開適用漏れを疑う具体的なアドバイスを表示し、トラブルシューティングを円滑にします。

### 7. Firebase Auth と Firestore 状態の同期タイムラグ対策
ログイン成功直後に発生しやすいアクセス権限エラー（Permission Denied）への対策です。

1. **認証監視とデータフェッチの分離**:
   - `onAuthStateChanged` の中での直接のデータフェッチ（`getDocs`, `getDoc`）を廃止し、独立した `[user, isAuthLoading]` 依存 of `useEffect` に処理を移行しました。これにより、Firebase SDK が内部的な認証トークンのセットアップを完全に完了したタイミングでクエリが実行され、同期ズレによるエラーが解消されます。
2. **FCMトークン自動同期の遅延ガード**:
   - ログイン直後の FCM トークン取得・保存（`getAndStoreToken`）において、Firestore への書き込みを行う前に 150ms のディレイを挟み、さらに `auth.currentUser` の認証確立状態をダブルチェックする防護ロジックを追加しました。

### 8. プロダクトグロース向け新機能
家族間でのカレンダー共有、過去スキャンの履歴閲覧、および実績の動的SNSシェアのための機能群です。

1. **家族シェア（カレンダー連携）機能**:
   - カレンダーデータストアを `groups/${groupId}/events` に移行・共通化しました。
   - 各ユーザーは固有の招待コード（`inviteCode`）を持ちます。UIからパートナーのコードを入力して連携すると、双方向でリアルタイムに同一のカレンダー同期（書き込み・読み込み）が実行されます。
   - 連携開始時に、それまで自分が登録した予定もパートナーの共有グループに自動マージされる親切設計です。
2. **おたよりスキャン履歴ダッシュボード**:
   - アプリケーション画面の「履歴一覧」タブから、過去にスキャンしたおたよりプリントの画像サムネイルと、自動抽出された予定の内容を一覧表示できます。
   - カード内の詳細ボタンから、既存の予定詳細モーダルを開いて確認・編集・削除・ICSエクスポートが可能です。
3. **動的OGP画像生成API (`/api/og`)**:
   - Next.js の `next/og` (`@vercel/og` Edge runtime) を活用した画像生成APIを新設しました。
   - `count` クエリパラメータ（例: `/api/og?count=12`）を付与してアクセスすると、「AIでおたよりの予定を 12件 自動化しました！」というスタイリッシュなブランドカラーのアイキャッチ画像を動的に描画して出力します。

### 9. 認証確立タイムラグに起因する権限エラー＆APIレスポンス安全設計
新規サインアップ完了時やログイン直後の初期ローディングにおけるPermission Denied、および決済API等のパースエラーを排除する対策です。

1. **データ同期初期処理への遅延（ディレイ）ガード適用**:
   - `syncData` の開始直後に `150ms` のディレイを挿入し、Firestoreクライアント側で認証トークンが完全に確立したことを保証した上でリクエストを実行するように堅牢化しました。これにより初期ロード時の権限エラー（Permission Denied）と、それに伴う招待コード「生成中...」でのフリーズを解消しました。
2. **新規サインアップ時の即時プロファイル初期作成**:
   - `handleEmailAuth` で新規アカウントが作成（サインアップ）された直後、クライアント側で即座に `users/{userId}` プロファイルドキュメント（初期グループID、招待コード）を `setDoc` で明示的に作成するようにしました。これにより、後続のカレンダーデータ取得でセキュリティルール上の `get()` （依存ドキュメントの読み込み）が Runtime Error を起こす問題が完全に解消されます。
3. **APIレスポンスの安全性強化 (JSONパースエラー防止)**:
   - クライアント側で `/api/checkout` などのAPIを fetch する際, `response.json()` を呼ぶ前に必ず `response.ok` をチェックするように変更しました。これにより、サーバーがHTMLエラー画面を返した際にも、フロントエンドがクラッシュせず安全に例外をキャッチして処理をハンドリングできるようになります。

### 10. エラー自動追跡のための強制ログ出力
インフラ起因（Firebase/Stripe/Vercel等）の不具合要因を開発者ツールおよびサーバーログで瞬時に追跡・特定するための設計です。

1. **データフェッチ工程 (`syncData`) でのリアルタイム状態出力**:
   - カレンダーデータ及びユーザープロファイルの取得が走る直前に、`auth.currentUser` の uid / email、およびフェッチ対象の `groups/${groupId}/events` パスを常に `console.log` で詳細出力するようにしました。
   - `catch` 時のエラーオブジェクト（`code`, `message`, `stack`, `rawError`）のダンプ機能も強化しています。
2. **決済APIルートでの環境変数監視と詳細追跡**:
   - `api/checkout/route.ts` 内に、StripeキーやFirebase管理認証情報（伏字処理済み）が正しくローディングされているかをチェックするデバッグログを組み込みました。また、Stripe SDK等から返ってくるエラー内容をサーバーログ（Vercel Log）およびクライアント側への JSON 応答内にすべて出力させ、原因の隠蔽を防ぎます。

### 11. Firestore取得直列化ガードの導入とStripe入力バリデーション
Firestoreでのレースコンディションによる Permission Denied、および決済時の不正な環境変数によるクラッシュの解消設計です。

1. **カレンダー取得クエリの直列化ガード (`if (!currentGroupId) return`)**:
   - `syncData` のデータ同期工程で、Firestoreから取得したプロファイルに `groupId` が完全に確定するまでは、イベントデータ取得（`getDocs`）に進まずに早期リターンする防衛ガードを組み込みました。これにより、プロファイルが未存在（または作成中）の状態でカレンダーの fetch が走り、セキュリティルール上の `get()` で Runtime Error となり Permission Denied になるのを100%防止します。
2. **Stripe Price ID に対する厳格なバリデーション**:
   - Vercel環境変数 `NEXT_PUBLIC_STRIPE_PRICE_ID` が登録されているものの値が空、または無効な指定である場合に Stripe SDK がクラッシュするのを防ぐため、IDが `price_` で始まる場合のみ Price ID として使い、それ以外は安全な `price_data` 生成方式へフォールバックするロジックに強化しました。

### 12. Firebase Admin 共通初期化ヘルパーの新設とセキュリティルール最適化
本番環境での環境変数パースの不具合、およびセキュリティルールの過剰なDB読み込みに伴う Permission Denied の解消設計です。

1. **`src/lib/firebaseAdmin.ts` 共通ヘルパーの新設**:
   - Vercel の環境変数に設定された `FIREBASE_SERVICE_ACCOUNT` の JSON 文字列に含まれる改行コード（`\n`）がエスケープ崩れを起こして `JSON.parse` が構文エラーになるのを防ぐための専用デコーダを実装しました。
   - すべての API エンドポイント（`checkout`, `events`, `scan`, `webhook`, `send-reminders`）の Firebase 管理者権限初期化処理をこの共通ヘルパーに一本化し、秘密鍵の `\\n` を物理的な改行文字 `\n` に復元してから Admin SDK に渡すように堅牢化しました。これにより 500 Internal Server Error によるクラッシュを完全に根絶しました。
2. **`firestore.rules` の高速パススルーと存在チェックガード**:
   - グループ予定の読み書き権限ルールにおいて、`groupId` が自分の UID と一致する（個人利用時）場合は、DB参照なしで無条件でパススルーするルールに最適化しました。
   - シェア連携時（`groupId != userId`）にのみ別ドキュメントの参照を行います。その際にも、事前に `exists()` による存在ガードを評価させることで、DBへのロード遅延発生時にもルール評価で Runtime Error (Permission Denied) を起こさないように堅牢化しました。

### 13. すべてのバックエンド API に対する Node.js ランタイムの明示的指定
Edge Runtime の誤干渉による Firebase / Stripe 関連 API の実行時強制終了（クラッシュ）の回避策です。

1. **`export const runtime = 'nodejs';` の強制適用**:
   - `api/og` での Edge Runtime の使用に伴う Vercel のビルドエンジンの推論エラーや、配下 API への Edge 適用の干渉を防ぐため、バックエンド API（`checkout`, `events`, `scan`, `webhook/stripe`, `cron/send-reminders`）のすべてのルートファイルにおいて、明示的に Node.js ランタイムを指定しました。
   - これにより、サーバーレス環境で Node.js ネイティブ依存を伴う初期化（Firebase Admin / Stripe インスタンス生成）が Vercel 側で不当に遮断（`FUNCTION_INVOCATION_FAILED`）される問題を完全に解消しました。

### 14. グローバルキャッシュを用いた Firebase Admin シングルトン初期化設計
サーバーレス環境および Next.js ホットリロード時の Firebase Admin SDK の二重初期化（DEFAULT app already exists）エラーの完全防止策です。

1. **`global` スコープによる App キャッシュ管理**:
   - Next.js のサーバーサイドコンテキスト再ロードやサーバーレス関数の再利用時に、メモリ上の `global` オブジェクトへ初期化済みの Firebase `App` インスタンスを退避・キャッシュさせるロジックを実装しました。
   - `getApps()` による既存 SDK 登録の確認と、`global.firebaseAdminApp` によるグローバルキャッシュの双方を評価した上で、未初期化の場合のみ `initializeApp` を走らせることで、複数エントリポイントでの二重初期化エラーによるプロセス例外クラッシュ（`FUNCTION_INVOCATION_FAILED`）を完璧に抑止しました。

### 15. 環境変数自動サニタイズユーティリティの導入と Stripe SDK の遅延初期化
環境変数の設定不備（スペースや改行の混入）によるモジュールロードフェーズでの即死クラッシュを完全に防ぐ防衛策です。

1. **`src/lib/envSanitizer.ts` の新規実装**:
   - 環境変数を読み込む際に、先頭・末尾の空白文字、目に見えない改行コード（`\r`, `\n`）、およびタブ文字を自動サニタイズして除去する専用ユーティリティ `sanitizeEnvVar` を導入しました。
   - `STRIPE_SECRET_KEY`, `NEXT_PUBLIC_STRIPE_PRICE_ID`, `FIREBASE_SERVICE_ACCOUNT` などの主要な環境変数のパース・初期化前にこのクリーンアップ処理を強制し、コピペミスによる障害を防止します。
2. **Stripe クライアントの遅延初期化（レイジーロード）**:
   - Webhook API（`api/webhook/stripe`）および決済 API（`api/checkout`）において、従来トップレベル（ロード時）で行われていた `new Stripe(...)` をリクエスト受信時の初回呼び出しタイミング（遅延）に移行しました。
   - これにより、環境変数の不備に起因する SDK の初期化エラーがモジュールロード時点で起きるのを防ぎ、かつ `POST` 内の最外殻 `try-catch` で確実に例外をキャッチして 500 エラーレスポンスとしてハンドリングできるよう堅牢化しました。

### 16. Firebase Admin SDK の完全遅延初期化（レイジーロード）の適用
モジュールロードフェーズ（インポート時）での未捕捉例外によるサーバープロセス即死クラッシュを完全に防ぐ防衛策です。

1. **完全遅延初期化（レイジーロード）への移行**:
   - `src/lib/firebaseAdmin.ts` 内での Firebase Admin SDK 初期化処理（`initializeApp`、および `getFirestore()` / `getAuth()` の実行）を、トップレベルから `getFirebaseAdmin()` 関数呼び出し時へと完全に遅延させました。
   - これにより、インポート（モジュールロード）の瞬間に環境変数のパース崩れや初期化エラーで Vercel コンテナプロセスが 0.04 秒で即死する挙動を完璧に根絶しました。
2. **キャッシュ判定の堅牢化**:
   - `global.firebaseAdminApp`、`global.firebaseAdminDb`、`global.firebaseAdminAuth` を併用してグローバル空間への完全なキャッシュ保管と検証を行い、実行フェーズにおける安全なシングルトン挙動を維持しています。

### 17. Stripe Checkout セッション生成時の Price ID 直接指定への移行
ルックアップキー検索や複雑なフォールバック判定に伴う API のオーバヘッドおよび無駄な API エラーを完全に防ぐ防衛策です。

### 18. APIレスポンスのエラーシリアライズ安全化と 200 正常返却による Vercel 即死防止
例外発生時に Vercel / Next.js のインフラ層で発生する二次的な JSON シリアライズ例外によるプロセス強制終了（FUNCTION_INVOCATION_FAILED）を防ぐ超防衛策です。

1. **例外の安全な文字列化 (シリアライズクラッシュ根絶)**:
   - `api/checkout` において、`error.stack` や `error.message` などの非シリアライズ可能な Error オブジェクトの生データをそのまま JSON 返却するのをやめ、すべて明示的に `String(error.message)` や `String(error.stack)` のようにプリミティブな文字列型にキャストして返却するようにしました。これにより、循環参照などによる `TypeError: Converting circular structure to JSON` クラッシュを防ぎます。
2. **`status: 200` 正常系にエラー情報を内包して返却するガード**:
   - Vercel や Next.js のゲートウェイ監視による 500 インフラエラー判定による遮断を防ぐため、初期化失敗や決済セッション作成失敗などのアプリ内例外発生時であっても `status: 200` でエラー情報 `{ success: false, error: '...' }` を応答する仕様に統一しました。
   - これに伴い、フロントエンド側（`page.tsx`）でも `response.ok` だけでなく、返却された JSON の `success === false` を適切に検知してエラーアラートを出すようにハンドリングを堅牢化しました。

### 19. プロセスレベルの未捕捉例外トラップによる非同期クラッシュ防止
SDK 等の非同期イベントループ上で発生した未捕捉の例外が同期 try-catch をバイパスしてサーバーレスプロセス全体を巻き込んで強制終了（即死）させる挙動を完全に遮断する防衛シールドです。

1. **プロセスイベントの監視とトラップ**:
   - `firebaseAdmin.ts` 共通ヘルパーおよび `api/checkout` API ルートの最上部において、Node.js プロセスの `unhandledRejection`（Promiseの未キャッチ例外）および `uncaughtException`（未捕捉の同期/非同期例外）の監視リスナーを登録しました。
   - これにより、Firebase 接続遅延時や Stripe の内部非同期エラー等によってプロセス全体が `FUNCTION_INVOCATION_FAILED`（即死）するのをプロセスレベルで完全にトラップして防止し、安全にログを出力してプロセスを生かしたままレスポンスを返却することを保証します。

### 20. API ルート（api/checkout）の完全自己完結（スタンドアロン）化によるロード時クラッシュ根絶
インポートフェーズ（モジュールロード時）における外部のローカルヘルパーモジュール起因の副作用・未捕捉例外を 100% 物理的に排除する絶対防衛アーキテクチャです。

### 21. Firebase Admin SDK の動的インポート（Dynamic Import）への切り替え
インポート時（コンテナ起動フェーズ）に発生するネイティブバイナリの読み込み衝突や初期化時クラッシュを 100% 回避しつつ、認証機能を安全に復旧させるアーキテクチャです。

1. **非同期 Dynamic Import への切り替え**:
   - `/api/checkout` の静的インポートを完全に抹消し、`POST` リクエストを受信した段階で初めて非同期 `await import('firebase-admin/app')` および `await import('firebase-admin/auth')` を実行して SDK を動的にロードする構造に書き換えました。
   - これにより、コンテナ立ち上げ時のモジュールロードの段階では `firebase-admin` のバイナリ読み込みや副作用を「完全にゼロ」に保ち、即死（`FUNCTION_INVOCATION_FAILED`）の可能性を完全に封じ込めました。
2. **認証機能とStripeメタデータuserIdの完全復旧**:
   - 動的インポートにより、決済リクエスト送信者の Firebase ID Token を検証し、取得した `userId` を Stripe Checkout セッションのメタデータ（`metadata.userId` および `subscription_data.metadata.userId`）に再度正しく紐付けました。これにより、本番の決済Webhookで誰が支払ったかを正確に検知する機能を復元しました。

### 22. フリーミウム戦略Bに伴う家族共有およびメンバー管理の書き込み・人数制限
無料プランとプレミアムプランの境界（有料・無料枠）を明確に定義し、プロダクト価値を高めるためのフリーミウム戦略Bアーキテクチャです。

1. **家族メンバー登録制限 (最大2名制限)**:
   - 無料プランのユーザーは自分を含む「最大2名」までしか家族メンバーを登録・色分けできません。3人目のメンバーを追加しようとした場合は警告が表示され、Stripe プレミアム登録への導線へとスムーズに誘導されます（プレミアムプランでは無制限に登録可能です）。
2. **家族間カレンダー共有の閲覧専用制限**:
   - 無料プランのユーザーは招待コードを用いてパートナーを「1名だけ」カレンダー共有に招待できます。ただし、招待された側は「閲覧専用（追加・編集・削除不可）」として扱われ、カレンダー上の操作や設定の変更がブロックされます。
   - カレンダー所有者がプレミアム会員であれば、招待された側も無制限に「双方向の共同編集（書き込み可能）」が開放されます。
3. **Firestore セキュリティルールおよび API レベルでの堅牢な書き込み制限**:
   - `firestore.rules` を強化し、`groups/{groupId}/events/{eventId}` に対する書き込み（`write`）を、グループオーナー本人か、もしくは共有相手でかつ**グループ所有者のプランがプレミアムプランである場合のみ許可**するよう設定しました。これにより、無料プランでの不正な共有書き込みを完全に遮断します。
   - `/api/events` および `/api/scan` の API ルートを dynamic import 化し、ロード時即死を防ぐ堅牢性を維持すると同時に、API レベルでも無料グループ共有ユーザーからの予定書き込み要求を 403 エラーで確実にブロックします。
